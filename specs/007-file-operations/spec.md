# Feature Specification: File Operations

**Feature Branch**: `007-file-operations`

**Created**: 2026-07-26

**Status**: Draft

**Input**: User description: "Add a new `opskit file` command group for local file inspection and safe conversion, per the newly-amended constitution Art. X (v1.3.0). Read-only diagnostic commands: line-ending detection, encoding/BOM detection, JSON/YAML/TOML/XML syntax validation, file-type sniffing, checksums, structural diff of JSON/YAML, cross-platform stat, duplicate-file finder. Guarded write commands (opt-in, non-destructive by default, atomic + non-clobbering `--in-place`): format conversion between JSON/YAML/XML/TOML, line-ending normalization (dos2unix/unix2dos), encoding transcoding, and pretty-printing. All commands follow the existing output contract (human-readable + `--json`/`--jsonl`, `NO_COLOR`, structured exit codes, batch semantics) and constitution Art. X's file-utility guarantees: named-target only, no network calls, non-destructive by default, atomic non-clobbering in-place writes, no content execution."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Catch a broken config file before it breaks something (Priority: P1)

An engineer has just hand-edited a JSON, YAML, TOML, or XML config file (or one was generated by
a script) and wants to know, before deploying or committing it, whether it is even syntactically
valid — and if not, exactly where the problem is — without spinning up the application that would
otherwise fail on it.

**Why this priority**: This is the highest-frequency, lowest-risk need in the category — a pure
read-only syntax check that saves a broken deploy or a confusing downstream failure, and it
requires no new safety machinery beyond what existing categories already have.

**Independent Test**: Point the command at a file with a deliberately introduced syntax error
(e.g., a trailing comma in JSON, bad indentation in YAML) and confirm it reports invalid with the
line/column of the problem; point it at a known-good file of each supported format and confirm it
reports valid.

**Acceptance Scenarios**:

1. **Given** a syntactically valid JSON, YAML, TOML, or XML file, **When** the user validates it,
   **Then** the output reports it as valid and the process exits 0.
2. **Given** a file with a syntax error, **When** the user validates it, **Then** the output
   reports it as invalid along with the line and column of the parse error, and the process exits
   with a distinct non-zero code for "invalid content" (not a usage error).
3. **Given** a file whose format is not specified explicitly, **When** the user validates it,
   **Then** the format is inferred from the file extension, falling back to content sniffing when
   the extension is missing or ambiguous, and the inferred format is stated in the output.
4. **Given** multiple files passed in one invocation, **When** the user validates them, **Then**
   every file is checked and reported individually — one invalid file does not stop the rest from
   being checked.

### User Story 2 - Normalize line endings without guessing what changed (Priority: P1)

An engineer has pulled a file (often from a Windows collaborator or a Windows-built artifact) with
the wrong line-ending convention for their toolchain — or the reverse — and needs both to *see*
what's actually in the file (is it CRLF, LF, or a mix?) and to *fix* it safely, without silently
clobbering the original if something goes wrong.

**Why this priority**: This is the specific "dos2unix" pain that motivated this feature, it is
extremely common, and it exercises the write-safety model that every other guarded command in this
feature also depends on — worth getting right first.

**Independent Test**: Create a file with mixed CRLF/LF line endings, run the detector and confirm
it reports the mix with counts; run the normalizer with `--to lf` without `--in-place` and confirm
the original file is untouched and the normalized content is written to stdout/a new file; re-run
with `--in-place` and confirm the original is atomically rewritten with LF endings and, when
`--backup` is passed, a backup of the pre-conversion content exists.

**Acceptance Scenarios**:

1. **Given** a file's line endings are requested, **When** the command runs, **Then** the output
   reports the counts of CRLF, LF, and lone-CR lines found and states whether the file is
   consistent or mixed.
2. **Given** a file is normalized to a target line-ending style without `--in-place`, **When** the
   command runs, **Then** the converted content is written to stdout (or an explicit output path)
   and the original file is left byte-for-byte unchanged.
3. **Given** a file is normalized with `--in-place`, **When** the command runs, **Then** the
   rewrite is atomic (the original is never left partially written, even if the process is
   interrupted) and, on success, the file's content has the requested line-ending style throughout.
4. **Given** `--in-place --backup` is used, **When** the command runs, **Then** a backup copy of
   the file's pre-conversion content exists at a predictable location after the command completes.
5. **Given** multiple files are passed to the normalizer, **When** the command runs, **Then** every
   file is processed independently and a failure on one file does not prevent the others from
   being converted.

### User Story 3 - Convert a file between structured data formats (Priority: P2)

An engineer needs to turn a JSON file into YAML (or the reverse), or bring in an XML or TOML file
and get it into a format their tool of choice actually accepts, without hand-transcribing it or
reaching for a one-off online converter of unknown trustworthiness. The same engineer sometimes
just wants a file's existing format reformatted — reindented, keys sorted — without changing its
data or format at all; this closely related capability (pretty-printing) shares the same
underlying parse/serialize machinery and write-safety rules as conversion, so it's delivered
alongside it.

**Why this priority**: This is the second most-requested capability behind line-ending
normalization and is the other headline use case for the feature, but it's lower-frequency than
User Story 1/2 for most engineers' day-to-day loop.

**Independent Test**: Convert a known JSON file to YAML, then convert the result back to JSON, and
confirm the data (keys/values/structure) round-trips correctly for JSON↔YAML↔TOML; convert a
representative XML file to JSON and confirm the documented element/attribute/text mapping is
applied consistently. Separately, pretty-print a compact JSON file with `--sort-keys` and confirm
the result is data-identical to the source (per a structural diff) with only formatting changed.

**Acceptance Scenarios**:

1. **Given** a valid JSON, YAML, or TOML file, **When** the user converts it to one of the other
   two formats, **Then** the output represents the same data (same keys, values, nesting) in the
   target format's syntax, and the process exits 0.
2. **Given** a valid XML file, **When** the user converts it to JSON or YAML, **Then** the output
   follows a documented, consistent element/attribute/text-content mapping, stated in the command's
   help text and docs.
3. **Given** the source file is invalid for its assumed format, **When** the user attempts a
   conversion, **Then** the command fails with the same invalid-content error `validate` would
   report (including line/column where available) rather than producing partial or malformed
   output.
4. **Given** no `--in-place` flag is passed, **When** a conversion runs, **Then** the result is
   written to stdout or an explicit `--output` path, and the source file is left unchanged.
5. **Given** `--in-place` is passed on a conversion that changes the file's format (not just its
   formatting), **When** the command runs, **Then** the file's content is replaced in the target
   format at the same path, atomically, subject to the same backup/no-clobber rules as User Story
   2.
6. **Given** a valid JSON, YAML, or XML file, **When** the user requests it be pretty-printed
   (optionally with a specific indent width and/or key sorting), **Then** the output has the
   requested formatting while representing exactly the same data as the source — no keys, values,
   or structure added, removed, or reordered beyond what `--sort-keys` explicitly requested.
7. **Given** a source file that is already invalid for its format, **When** the user requests
   pretty-printing, **Then** the command fails with the same invalid-content error `validate`
   would report, rather than producing reformatted-but-wrong output.

### User Story 4 - Verify and identify a file of unknown or unverified provenance (Priority: P2)

An engineer has a file that arrived from somewhere they don't fully trust the labeling of — a
download, an artifact from a build, a file with a suspicious or missing extension — and wants to
know what it actually is (independent of its name) and/or get a checksum to compare against a
known-good value, before opening or shipping it further.

**Why this priority**: This is a distinct, common troubleshooting need ("is this really a JSON
file, or is it HTML from a failed request that got saved with the wrong extension?") that pairs
naturally with the checksum use case, but is less universally needed than syntax validation or
line-ending fixes.

**Independent Test**: Rename a JSON file to have a `.txt` extension, run the identifier, and
confirm it reports the actual detected type and flags the extension mismatch; compute a checksum
for a file and confirm it matches an independently computed checksum of the same content.

**Acceptance Scenarios**:

1. **Given** a file, **When** the user requests its type, **Then** the output reports the detected
   type based on content (magic bytes / structural sniffing), independent of the file's extension.
2. **Given** a file whose extension does not match its detected content type, **When** the user
   requests its type, **Then** the mismatch is explicitly flagged in the output rather than
   silently reported as just one or the other.
3. **Given** one or more files, **When** the user requests a checksum, **Then** the output reports
   each file's hash using the requested algorithm (defaulting to a documented default), and every
   file is processed even if one is unreadable.
4. **Given** a path that does not exist or is not a regular file, **When** identification or
   hashing is requested, **Then** that target is reported as a distinct failure without aborting
   the rest of a batch.

### User Story 5 - Diagnose and fix a text-encoding problem (Priority: P3)

An engineer sees mojibake or a decode error when a tool reads a text file and needs to know what
encoding the file is actually in (and whether it has a BOM) before deciding how to fix it — or, once
diagnosed, transcode it to the encoding their toolchain expects.

**Why this priority**: Genuinely useful but a narrower, less frequent need than the structured-data
and line-ending scenarios above — it's the "when things have already gone wrong" case rather than
routine hygiene.

**Independent Test**: Create files with UTF-8 (with and without BOM), UTF-16, and Latin-1 encodings
containing non-ASCII characters; confirm the detector correctly reports each one's encoding and BOM
status; transcode the Latin-1 file to UTF-8 and confirm the resulting bytes decode correctly and
round-trip the original characters.

**Acceptance Scenarios**:

1. **Given** a text file, **When** the user requests its encoding, **Then** the output reports the
   detected encoding and whether a byte-order mark is present.
2. **Given** a file containing byte sequences invalid for its apparent encoding, **When** the user
   requests its encoding, **Then** the invalid sequences are flagged rather than silently ignored
   or mis-decoded.
3. **Given** a file in a known source encoding, **When** the user transcodes it to a target
   encoding, **Then** the resulting content, when decoded with the target encoding, reproduces the
   original text, and the write follows the same default-to-stdout / opt-in `--in-place` /
   atomic / backup rules as User Stories 2 and 3.
4. **Given** a target encoding cannot represent a character present in the source text, **When**
   transcoding is attempted, **Then** the command fails with an actionable error identifying the
   problem character rather than silently substituting or dropping it.

### User Story 6 - Compare structured files and find duplicates (Priority: P3)

An engineer wants to know whether two JSON or YAML files are meaningfully the same (ignoring key
order and formatting differences) rather than doing a line-by-line text diff that's noisy for
reformatted files, or wants to find redundant copies of files cluttering a directory tree.

**Why this priority**: Both are useful, occasional troubleshooting/cleanup aids rather than
everyday operations, and neither writes anything to disk.

**Independent Test**: Create two YAML files with identical data but different key ordering and
indentation, confirm the structural diff reports them as equivalent; introduce one differing value
and confirm the diff pinpoints the differing key/path; create two files with identical content in
a directory tree and confirm the duplicate finder groups them together.

**Acceptance Scenarios**:

1. **Given** two structured files (JSON or YAML) with identical data but different formatting or
   key order, **When** the user diffs them, **Then** the output reports them as equivalent.
2. **Given** two structured files that differ in one or more values, **When** the user diffs them,
   **Then** the output identifies the specific key path(s) and the differing values on each side.
3. **Given** a directory, **When** the user searches it for duplicate files, **Then** files with
   identical content are grouped together in the output, and files with unique content are not
   reported as duplicates of anything.
4. **Given** the `--recursive` flag is not passed, **When** duplicate search runs, **Then** only
   files directly in the given directory are considered (not subdirectories); with the flag, the
   whole tree is considered.

### User Story 7 - Inspect file metadata and use everything from code (Priority: P3)

An engineer wants a cross-platform-normalized view of a file's permissions, owner, size,
modification time, and symlink target (replacing `stat`/`Get-Item`-style OS-specific tools), and a
platform engineer wants to call any of the above capabilities from their own scripts via a typed
API rather than shelling out to the CLI.

**Why this priority**: Metadata inspection is a small, low-risk convenience, and API parity is a
constitutional guarantee that serves the flows above rather than standing alone — both round out
the category without being its primary draw.

**Independent Test**: Run the stat command against a file with known permissions/size/mtime and a
symlink, and confirm all fields are reported and normalized the same way conceptually on every
supported OS. From a script, call a diagnostic function and a guarded write function
programmatically, read the typed result, and catch a typed error for an induced failure.

**Acceptance Scenarios**:

1. **Given** a regular file, **When** the user requests its stat info, **Then** the output reports
   size, owner (where determinable without elevated privileges), permissions, and last-modified
   time in a cross-platform-normalized form.
2. **Given** a symbolic link, **When** the user requests its stat info, **Then** the output reports
   the link's target path in addition to the link's own metadata.
3. **Given** the library interface, **When** a diagnostic or guarded-write call succeeds, **Then**
   the caller receives a typed result exposing the same fields as the CLI output, and nothing is
   printed or written unless the call explicitly requested a write.
4. **Given** an induced failure (e.g., a nonexistent path, or a target that is a directory where a
   file is required), **When** the call runs programmatically, **Then** a typed exception of the
   matching failure class is raised with an actionable message.

### Edge Cases

- **Target path does not exist, is a directory where a file is expected, or is unreadable**:
  reported as a distinct failure for that target, never crashing the batch or silently skipping it.
- **Empty file**: diagnostics report it as empty rather than erroring; conversions/normalizations
  of an empty file succeed and produce an empty (but validly-formatted, where applicable) result.
- **File larger than available memory allows to process at once**: hashing and line-ending
  detection stream the file rather than loading it wholesale; very large structured files may be
  limited by the parser's own memory needs, and such limits are surfaced as an actionable error
  rather than an unhandled crash.
- **`--in-place` requested on a read-only file or a path without write permission**: fails with an
  actionable permission error; the original file is left untouched.
- **`--in-place` without `--backup`, and the process is interrupted mid-write**: the atomic
  write/rename guarantees the original file is never left partially written — either the old
  content or the new content is present, never a corrupt mix.
- **`--backup` requested but a backup file already exists at the destination**: does not silently
  overwrite the pre-existing backup; requires the same explicit-overwrite opt-in as any other
  clobber.
- **Structured-format conversion where the source is valid but ambiguous for the target format**
  (e.g., duplicate keys, non-string map keys, XML mixed content): handled per a documented,
  consistent convention rather than silently dropping data; where information would be lost, the
  command says so rather than pretending the conversion is lossless.
- **File-type sniffing on a file too short to contain a recognizable signature**: reported as
  "undetermined" rather than guessed at.
- **Binary file passed to a text-oriented command** (validate, encoding, eol, reencode, pretty,
  diff): reported as a distinct "not a text/structured file" failure rather than a garbled attempt
  to process it.
- **Two identical file paths passed to `diff`**: reported as equivalent, not an error.
- **`duplicates` run on an empty directory or one with no duplicates**: reported as no duplicates
  found, not an error.

## Requirements *(mandatory)*

### Functional Requirements

**Read-only diagnostics**

- **FR-001**: Users MUST be able to check one or more files' line-ending style and receive, per
  file, counts of CRLF/LF/lone-CR occurrences and whether the file is consistent or mixed.
- **FR-002**: Users MUST be able to detect a file's text encoding and byte-order-mark presence, and
  have invalid byte sequences for the detected encoding flagged.
- **FR-003**: Users MUST be able to validate the syntax of a JSON, YAML, TOML, or XML file, with
  format auto-detected from extension/content or explicitly overridden, and receive the line and
  column of any syntax error found.
- **FR-004**: Users MUST be able to identify a file's actual type via content sniffing independent
  of its extension, with an explicit flag when the extension and detected content disagree.
- **FR-005**: Users MUST be able to compute a checksum (from a documented set of supported
  algorithms, with a documented default) for one or more files.
- **FR-006**: Users MUST be able to perform a structural (semantic) comparison of two JSON or YAML
  files that reports equivalence when formatting/key-order differs, and pinpoints differing key
  paths and values when data actually differs.
- **FR-007**: Users MUST be able to retrieve a cross-platform-normalized metadata summary (size,
  permissions, owner where determinable, last-modified time, symlink target if applicable) for one
  or more files.
- **FR-008**: Users MUST be able to search a directory for files with identical content, with an
  explicit flag controlling whether the search recurses into subdirectories, and receive the
  results grouped by identical content.
- **FR-009**: None of the commands in this requirement group MUST modify, move, delete, or create
  any file, directory, or perform any network call.

**Guarded write commands**

- **FR-010**: Users MUST be able to convert a JSON, YAML, TOML, or XML file's content into any of
  the other three formats, preserving the source data per a documented, consistent mapping.
- **FR-011**: Users MUST be able to normalize a file's line endings to a specified target style
  (e.g., LF or CRLF).
- **FR-012**: Users MUST be able to transcode a file from one text encoding to another, with the
  source encoding auto-detected or explicitly specified.
- **FR-013**: Users MUST be able to reformat/pretty-print a JSON, YAML, or XML file (e.g.,
  normalized indentation, optional key sorting) without changing its data.
- **FR-014**: Every guarded write command MUST operate only on files explicitly named by the
  operator — a single path, or, for a command that does not change a file's format or encoding
  (i.e. `eol`), a batch list — and MUST perform no network call.
- **FR-015**: Every guarded write command MUST default to non-destructive output (stdout or an
  explicit new-file path) and MUST require an explicit `--in-place` opt-in to modify the named
  source file.
- **FR-016**: When `--in-place` is used, the write MUST be atomic (the original file is never left
  partially written) and MUST NOT silently overwrite a pre-existing, unrelated file (e.g., an
  existing backup destination); overwriting an existing file requires an explicit `--backup` or
  equivalent force opt-in.
- **FR-017**: No guarded write command MUST execute, evaluate, or otherwise treat file content as
  code — content is only parsed and transformed as data.
- **FR-018**: When a requested conversion or transcoding cannot preserve the source data or
  characters exactly (lossy conversion), the command MUST report this rather than silently
  discarding information.

**Contracts (per constitution)**

- **FR-019**: The command group MUST honor the opskit output contract: human-readable default,
  versioned JSON envelope, `--jsonl` where a command is batchable, `NO_COLOR`/auto-plain behavior,
  and structured exit codes with distinct classes for usage error, invalid-content, path-not-found/
  permission-denied, clobber-refused (FR-016's no-clobber guarantee), and success.
- **FR-020**: Batchable commands (multiple targets via arguments, `--input-file`, or stdin) MUST
  process every target — a failure on one target MUST NOT abort processing of the rest — and the
  process exit code MUST be 0 only if every target succeeded, the shared outcome's code if uniform
  across all failures, or the partial-result code otherwise.
- **FR-021**: Every capability in this feature MUST be available programmatically with typed
  results and typed errors; the programmatic layer never prints to stdout/stderr or terminates the
  process.
- **FR-022**: Behavior MUST be identical on Windows, macOS, and Linux, including atomic-write and
  line-ending semantics, except where a platform genuinely cannot expose a piece of metadata (e.g.,
  POSIX-style owner/permission bits on Windows), in which case the gap MUST be explicitly
  attributable in the output rather than silently inconsistent or fabricated.

### Key Entities

- **File Target**: an operator-named file (or batch of files) that a command operates on; carries
  the resolved path, detected/declared format, and detected/declared encoding.
- **Line-Ending Report**: the outcome of a line-ending check — per-file counts of CRLF/LF/lone-CR
  and a consistent/mixed classification.
- **Encoding Report**: the outcome of an encoding check — detected encoding, BOM presence, and any
  invalid byte sequences found.
- **Validation Result**: the outcome of a syntax check — valid/invalid, detected format, and (if
  invalid) the line/column and message of the parse error.
- **Identification Result**: the outcome of a type-sniffing check — detected type, the file's
  extension, and whether they agree.
- **Checksum Result**: a file's path, the algorithm used, and the resulting digest.
- **Structural Diff Result**: the outcome of comparing two structured files — equivalent, or a list
  of differing key paths with the value on each side.
- **Stat Result**: a file's normalized metadata — size, permissions, owner (if determinable),
  last-modified time, and symlink target (if applicable).
- **Duplicate Group**: a set of two or more files sharing identical content, and the content hash
  that groups them.
- **Conversion Result**: the outcome of a guarded write command — source and target format/
  encoding/line-ending style, destination (stdout, new file, or in-place), whether a backup was
  created, and whether the conversion was lossless.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: An engineer can validate a structured config file and get a pass/fail result with an
  exact error location (when invalid) in under 5 seconds, for any of the four supported formats.
- **SC-002**: An engineer can detect and fix inconsistent line endings in a file, with the original
  file provably unchanged unless `--in-place` was explicitly requested — verified by a test that
  hashes the source file before and after a non-in-place run.
- **SC-003**: A guarded write command interrupted mid-operation (simulated failure during an
  in-place write) never leaves the target file partially written — verified by fault-injection
  tests around the atomic-write step.
- **SC-004**: Converting a file between any two of JSON/YAML/TOML and converting it back reproduces
  the original data with no loss, verified by round-trip tests across representative fixtures.
- **SC-005**: All read-only diagnostics and all guarded write commands produce structurally
  identical reports and file outputs on Windows, macOS, and Linux, verified by the CI matrix, with
  any platform-specific unavailable field explicitly named rather than silently omitted.
- **SC-006**: Every capability in this feature is usable programmatically with typed results and
  typed errors; the documented examples run as written.
- **SC-007**: A batch of files passed to any batchable command is fully processed even when a
  subset fail, verified by a fixture batch that mixes valid, invalid, and inaccessible files.

## Assumptions

- **XML↔JSON/YAML conversion uses a documented, fixed convention** (element names become keys,
  attributes are namespaced under a dedicated key such as `@attributes`, text content under a
  dedicated key such as `#text`) rather than a fully generic/lossless XML data model — this is the
  well-established convention used by comparable tools and keeps the mapping predictable, at the
  cost of not perfectly round-tripping unusual XML shapes (mixed content, namespaces); such
  lossiness is surfaced per FR-018 rather than silently accepted.
- **Guarded write commands that change format or encoding (`convert`, `reencode`) operate on one
  source file per invocation**, while commands that don't change the file's identity (`eol`, and
  read-only diagnostics) accept a batch of files — because a batch of format conversions would
  require a batch-naming convention for outputs that adds complexity without a clearly demonstrated
  need in v1; this may be revisited if requested.
- **Default output destination for guarded write commands without `--in-place` is stdout**, with an
  optional explicit `--output <path>` to write a new file instead — chosen for consistency with
  Unix-style filter tools and to keep "non-destructive by default" unambiguous (nothing is written
  to disk at all unless the operator names a destination or opts into `--in-place`).
- **`--backup` writes a sibling file with a fixed, documented suffix** (e.g. `<file>.bak`) in the
  same directory as the source, not a configurable backup directory — the simplest predictable
  behavior for v1; a pre-existing file at that path is treated as a clobber target subject to the
  same overwrite rules as any other destination.
- **Default checksum algorithm is SHA-256** when `--algo` is not specified, with MD5/SHA-1 offered
  for interoperability with legacy checksums rather than as a security recommendation.
- **No file size or count limit is imposed in v1** beyond what streaming/parser memory naturally
  allows; very large individual structured files may hit parser-library limits, which are surfaced
  as actionable errors rather than crashes.
- **Symbolic links are not followed/expanded during `duplicates` traversal**, matching the
  precedent set by storage diagnostics, to avoid double-counting and cycles.
- **Pretty-printing normalizes formatting only** (indentation, key order if `--sort-keys` is
  passed) and never changes the underlying data, distinguishing it from `convert` (which changes
  format) and `eol` (which changes line endings only).
